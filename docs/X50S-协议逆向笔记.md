# 352 X50S 空气净化器 · 局域网协议逆向笔记

来源：`Desktop/352-apk`（`com.bugull.threefivetwoaircleaner`，dex 已解析）
关键类：
- `network/wifi/newwifi/protocal/CleanerWifiProtocol` —— 端口、命令码、固定码
- `network/wifi/newwifi/protocal/CleanerDeviceProtocol` —— 设备侧命令/参数表
- `network/wifi/newwifi/protocal/builder/ProtocolHeaderBuilder` —— 16 字节外层头
- `network/wifi/newwifi/protocal/builder/DeviceCommandBuilder` —— 内层帧构造
- `network/wifi/b/g` —— 收包分发（`NetworkResponseParser`）
- `network/wifi/b/a` —— **X50 系状态解析**（`AirCleaner50DataParser`）
- `ui/control/f/u/c0` —— X50 主页 presenter（真正发控制命令的地方）

---

## 0. 结论速览

- X50S 在局域网里就是 **X50 家族**：设备类型 `0x03`，界面和解析器与 X50 完全共用
  （`DeviceType.TYPE_X50S` 的 `value` 与 X50 同为 5；协议分发只认 2=X83 / 3=X50 / 4=G30）。
- 局域网走 **UDP 11530**；公网中继走 **TCP 11591 / 352.yunext.com**。
- 控制/状态用的是 **`F0 72` 内层帧**，外面套 16 字节 `A1 04 ...` 头。
- APK 里还有一套老的 **`A5 A0` 单字节校验帧**（X83 系列用，HA 社区集成 `ha-352-airpurifier` 用的就是它），
  两套不要混用。
- **实测：X50S 不回应 IPv4 广播，只回应单播。** 发现设备时必须向具体 IP 再发一份。
- 设备会定期主动推送状态帧，不需要轮询。

## 1. 外层帧（两套内层帧共用）

16 字节定长头，长度字段在 `[8]`：

```
off  size  含义
0    1     0xA1              协议版本（PROTOCOL_VERSION）
1    1     0x04              地址类型/标志；bit1、bit2 在应答里有意义
2    6     MAC               设备 MAC，正常顺序（00 95 69 D7 9B FE）
8    1     LEN               总长 - 9
9    1     0x00              保留
10   2     SEQ               包序号，大端（0..32767 循环）
12   1     COMPANY           厂商码：0xF1 = LRD（352 自有），0xF2 = HF
13   1     DEV_TYPE          设备类型：2=X83 3=X50/X50S 4=G30 1=M25
14   2     AUTH              认证码，大端（来自云端下发，如 0x22B5）
16   ...   CONTENT           命令内容
```

`LEN = 总长度 - 9`。例：整帧 32 字节时 LEN=0x17。

请求的 CONTENT 有两种写法：
- **带通道字节**：`[channel][内层帧]`，`channel` 由设备类型决定
  （`1→03`，`2/3/4→01`，其它 `→00`）。控制命令走这种。
- **直接命令字节**：`[cmd][参数...]`，搜索/订阅/心跳等走这种。

## 2. 内层帧 `F0 72`（X50S 控制与状态）

### 2.1 请求

```
off  size  含义
0    1     0xF0              PRO_DEVICE_STX[0]
1    1     0x72              PRO_DEVICE_STX[1]
2    2     LEN               内层长度 - 2，大端
4    1     DEV_TYPE          0x03（X50/X50S）
5    1     0x04              固定
6    1     CMD               0x02 = 控制/查询（APP_TO_AC 方向）
7    2     SEQ               命令序号，大端
9    1     SUB               0x03 = 数据长度为 3
10   1     P5                参数类型
11   1     P6                参数值
12   1     0x00              保留
13   2     CRC16             见第 3 节，覆盖 [2 .. len-3]
```

### 2.2 状态上报（设备 → App）

```
0    1     0xF0
1    1     0x72
2    2     LEN
4    1     DEV_TYPE
5    1     0x84              0x04 | 0x80：应答标志位
6    1     0x02              命令回显
7    ...   STATUS[0..]       状态数据，见第 6 节
末 2  CRC16                  覆盖 [2 .. len-3]
```

外层 CONTENT = `02` + 上述内层帧，所以**整帧从 offset 24 开始就是 STATUS[0]**。

分发判据（`network/wifi/b/g`）：`帧[16]==0x02` 时，
`帧[13]==2` 走 X83 解析器、`==3` 走 X50 解析器、`==4` 走 G30 解析器。

## 3. CRC16（352 私有，注意最后取反）

CCITT 多项式 `0x1021`，初值 `0xFFFF`，MSB-first，**结果按位取反**，高字节在前：

```python
def crc16(data: bytes) -> bytes:
    crc = 0xFFFF
    for b in data:
        for i in range(8):
            msb = (crc & 0x8000) >> 8
            bit = (b << i) & 0x80
            crc = (crc << 1) & 0xFFFF
            if msb ^ bit:
                crc ^= 0x1021
    crc = (~crc) & 0xFFFF
    return bytes([crc >> 8, crc & 0xFF])
```

覆盖范围：内层帧 `[2 : len-2]`（即长度字段起、到 CRC 前），不含 `F0 72` 和 CRC 自身。

## 5. 控制命令（X50S 实际使用的通道）

`DeviceCommandBuilder.controlDeviceCommand(dev, P5, P6)` 生成的内层帧：

```
F0 72 00 0D 03 04 02 [seqH] [seqL] 03 [P5] [P6] 00 [crcH] [crcL]
```

外层再补 `01` 作为通道字节。已确认被 X50 presenter（`ui/control/f/u/c0`）调用的：

| 功能 | P5 | P6 | 说明 |
|---|---|---|---|
| 查询/同步状态 | `0x11` | `0x11` | 进页面先发一次 |
| 电源 | `0x5E` | `0x00` 开 / `0x11` 关 | 实测生效 |
| 模式 | `0x51` | `01` 自动 / `02` 睡眠 / `03` 极速 / `04` 手动 | **实测：`0x04` 才是手动，`0x05` 设备无响应** |
| 风速 | `0x52` | `01`–`05` | X50S 实测 1–5 档，设 6 无效 |
| 灯光 | `0x56` | `0x00` 开 / `0x11` 关 | 实测生效 |
| 童锁 | `0x55` | `0x00` 开 / `0x11` 关 | **实测生效**（原为推断） |
| 定时 | `0x54` | `0/1/2/3/5/8` | **实测无响应，X50S 不支持** |

同一套 `P5` 语义在旧 `A5 A0` 帧里也存在（X83 用），可作旁证：
`0x53` PTC（0/1/2）、`0x55` 童锁（0 开 / 17 关）、`0x57` 滤芯位置（1/2/3）。
`0x53` 和 `0x57` 尚未在 X50S 上实测。

> 注意：App 常量表把 `0x05` 标成手动，那是老固件的取值。
> X50S（`auth=0x1D05`、`company=0xF2` 的机型）必须用 `0x04`。

示例（电源开，MAC 00:95:69:D7:9B:FE，company F1，type 03，auth 22B5，seq 3）：

```
A1 04 00 95 69 D7 9B FE 17 00 00 03 F1 03 22 B5 01
F0 72 00 0D 03 04 02 00 03 03 5E 00 00 D1 C0
```

## 6. 状态数据字段（X50S，整帧 offset 24 起）

设 `S = 帧[24:]`（`S[0]` 是内层帧里 CMD 回显后的第一个数据字节）：

| 字段 | 偏移 | 编码 |
|---|---|---|
| 模式 | `S[3] & 0x0F` | 1 自动 / 2 睡眠 / 3 极速 / 4 手动 |
| 滤芯类型 | `S[3] >> 4` | 1 = 标准，2 = 超级碳，其它 = 0 |
| 风速 | `S[4]` | 1–5；极速模式会跑到 6 |
| 定时 | `S[5]` | 0 / 1 / 2 / 3 / 5 / 8 小时（X50S 恒为 0） |
| 空气质量 | `S[6]` | 1–3 |
| 童锁 | `S[7]` | 0 = 开，17 = 关 |
| 灯光 | `S[8]` | 0 = 开，17 = 关 |
| 电源 | `S[9]` | 0 = 开，17 = 关 |
| 累计定时 | `S[10..11]` | 大端 |
| PM2.5 | `S[12..13]` | 大端 |
| 温度 | `S[14]` | ℃；**X50S 恒为 0** |
| 湿度 | `S[15]` | %；**X50S 恒为 0** |
| CO₂ | `S[16..17]` | 大端；**X50S 恒为 0** |
| PTC | `S[18]` | |
| 累计运行时间 | `S[19..20]` | 大端；>65059 或 10000–65000 视为无效归 0 |
| 净化量倍率 | `S[21]` | 0/1/2/3 → ×1/×10/×100/×1000 |
| 净化量 | `S[22..23]` | 大端 × 倍率；**X50S 恒为 0** |
| 累计净化倍率 | `S[24]` | 同上 |
| 累计净化量 | `S[25..26]` | 大端 × 倍率；**X50S 的实际数据在这里** |
| 联动状态 | `S[29]` | |

字段与社区 HA 集成的 `base=24` 完全对上，可交叉验证。

> 实测一台 X50S：`S[25..26]` 约 405140 m³，而 `S[22..23]` 恒为 0。
> 所以「累计净化量」应该取后者那个字段，前面那个可能是给其它型号留的。

## 7. 扩展命令（同样是 `F0 72` 帧）

### 7.1 定时开关机组（CMD = `0x0B`）

内层：`F0 72 00 2D 03 04 0B [seq2] 04 20 <4 组 × 8 字节> <SUM> <CRC2>`

每组 8 字节：`+2` 星期位掩码（bit7=启用，bit6..0 = 一..日），
`+3/+4` 开机时/分，`+5/+6` 关机时/分，`+7` 保留。
`SUM` 是数据段字节和（不是 CRC）。

### 7.2 滤芯写入（CMD = `0x04`，43 字节）

`F0 72 00 29 03 04 04 [seq2] <滤芯位置> <滤芯 SN 17 字节> <报警阈值> <总寿命2B> <已用2B> ... CRC`

### 7.3 滤芯状态/搜索

- `0x03`：滤芯状态查询（12 字节）
- `0x06`：滤芯搜索（16 字节）
- 旧式 `A5 A3` 帧还提供"发 SN 码"（末尾单字节和校验）

### 7.4 检测仪模式 / 自动最低风速（CMD = `0x0C` / `0x0B`）

`demandDetectorMode(dev, 3)`：`F0 72 00 0C 03 04 0C [seq2] 01 03 03 <CRC>`

## 8. X50S 特有：滤芯预警

X50 系应答 `0x84 0x0C` 子帧：

| 条件 | 含义 |
|---|---|
| `content[6]=0x84, content[7]=0x0C, content[11]=0x03` | 滤芯信息 |
| 同上，`content[11]=0x04` | 定时组（4 组，见 7.1） |
| 同上，`content[11]=0x06` | **滤芯预警值 = `content[13]`** |

`content[13]` 对应 `Device.setShowFilterWarning()`，就是界面上
`showX50sFilterWarning` / `tvX50sFilterInfo` 显示的内容（百分比）。

> 这里的 `content[11]` 取值是从解析分支反推的（解析器只按这三个值分行为），
> 三个值各代表什么业务含义需要抓包确认。

## 9. 与旧 `A5 A0` 帧的区别（重要）

APK 里同时存在两套内层帧：

- **`F0 72`（本文主述）**：X50/X50S/G30 新固件。16 字节外层头 + 通道字节 + CRC16。
- **`A5 A0`（老帧）**：X83/X83C。CONTENT = `[channel][A5 A0 P5 P6 00 00 SUM]`，
  `SUM` 是**单字节累加和**（`d.a.a()` 追加），没有 CRC16。

社区的 `ha-352-airpurifier` 集成用的是 `A1 04 MAC 0E 00 ... F1 03 05 04 01 A5 A0 ...`
这类老帧。如果 X50S 固件只认 `F0 72` 帧，那么拿这套集成去控制就会没有反应，
状态也可能对不上——这是最值得先验证的差异点。

## 10. 自己构造/验证的建议

1. 先发搜索帧，确认应答里 `帧[17..20]` 的 4 字节设备类型 —— 这是判断 X50S 是 `0x03` 的**最终依据**。
2. 用App 操作一次，同时抓 UDP 11530（PCAPdroid / 路由器镜像 / 电脑热点），
   对照本文的 `SEQ`、`P5/P6` 和 CRC。
3. 校验 CRC 时注意最后一步取反；先用本文示例帧对齐实现。
4. 状态是设备主动推送 + `0x11 0x11` 查询触发，不需要轮询。

## 12. 实机验证记录（2026-10）

在一台 X50S 上验证（`MAC=F0:FE:6B:93:88:FF`、`company=0xF2`、`auth=0x1D05`）：

### 已验证

- 开关机（`0x5E`）、风速 1–5（`0x52`）、模式（`0x51`）、
  灯光（`0x56`）、童锁（`0x55`）全部生效
- 搜索帧用 App 固定码 `0xCB76` 不需要设备真实认证码
- 设备会定期主动推送状态（`local_push` 成立）
- CRC16 实现与设备一致（发出的帧被设备接受并正确应答）

### 修正了原先的推断

| 项 | 原推断 | 实测结果 |
|---|---|---|
| 手动模式 P6 | `0x05` | **`0x04`**，`0x05` 无响应 |
| 定时 `0x54` | 可用 | **无响应**，不支持 |
| 温湿度/CO₂ | 可用 | **恒为 0**，无这些传感器 |
| 累计净化量 | `S[22..23]` | **`S[25..26]`** |
| 风速档数 | 6 | **5**（极速模式例外，会跑到 6） |

### 一个关键网络行为

**设备不回应 IPv4 广播（`255.255.255.255`），只回应单播。**
所以发现设备时必须同时向具体 IP 发一份，只发广播会一直显示离线。
